Contexto

Por que o Devin muda o jogo no banco

30–40% do tempo de um engenheiro em banco vai para tarefas mecânicas. O Devin assume isso.

O problema do dia a dia
Criar boilerplate, escrever testes repetitivos, gerar documentação, criar Dockerfiles — tarefas necessárias mas que não exigem seu julgamento como engenheiro. Em um banco com centenas de microserviços, esse overhead se multiplica.
O Devin é o agente que assume essas tarefas, liberando você para focar no que exige julgamento real: arquitetura, decisões de negócio, e revisão de código crítico.
O modelo mental correto
Trate o Devin como um dev júnior extremamente competente e disponível 24h. Você passa a tarefa com clareza, ele executa e reporta. Você revisa e aprova o que importa.
O Devin não é um autocomplete turbinado. É um software engineer autônomo que lê sua codebase, entende o que precisa ser feito, planeja os passos, e executa — tudo em uma sessão.

Por que contexto bancário no prompt é obrigatório

O Devin não sabe que você trabalha em banco. Sem contexto explícito, ele vai produzir código correto tecnicamente mas errado para o seu ambiente:

❌ CPF aparece em logs de erro → violação LGPD
❌ Timeout de 30s em webhook → viola SLA do banco
❌ Sem audit log em operações financeiras → violação BACEN
✅ Sempre inclua no prompt: "Este serviço processa [tipo de dado] para [tipo de operação]. Requisitos: [compliance, SLA, segurança]"
Vocabulário essencial
Agente autônomo
Software que percebe o ambiente, planeja e executa ações de forma independente para atingir um objetivo — sem intervenção passo a passo do usuário.
Prompt de engenharia
Instrução técnica estruturada com contexto, tarefa específica e critérios de aceitação. A qualidade do output é diretamente proporcional à clareza do prompt.
Tool use
Capacidade do Devin de chamar ferramentas reais (terminal, editor de código, GitHub) durante a execução, além de apenas gerar texto.
Context window
Limite de informação por sessão. Tarefas muito grandes (>6h equivalente) fazem o agente "perder o fio". Regra: E1–E2 máximo 2h por sessão.
Scaffolding
Estrutura inicial fornecida ao agente (código base, templates, configs) que delimita o escopo e melhora a qualidade do output.
Grounding
Ancoragem do agente em fontes de verdade verificáveis (codebase atual, docs oficiais, testes) para evitar alucinações técnicas.
Demonstração Prática

API bancária: endpoints de health & status

Cenário NTT: A API de autenticação do banco precisa de probes para o Kubernetes e informações operacionais para o SRE team.

O prompt (estrutura para todos os níveis)
Prompt Enviar ao Devin 
Contexto: API REST em Node.js/Express que faz autenticação de usuários para
sistema bancário. O serviço roda em Kubernetes e precisa de probes de saúde.
Compliance: dados de autenticação são sensíveis — nenhuma credencial ou token
em logs.

Tarefa: Implementar dois endpoints:

1. GET /health
   Response: { "status": "ok", "timestamp": "<ISO 8601>" }
   HTTP 200 quando saudável, HTTP 503 quando não

2. GET /status
   Response: {
     "service": "auth-api",
     "version": "<valor da ENV AUTH_API_VERSION>",
     "uptime_seconds": <segundos desde startup>,
     "timestamp": "<ISO 8601>"
   }

Critérios de aceitação:
- Endpoints respondem em menos de 50ms (sem dependências externas)
- Nenhuma informação sensível na response ou nos logs
- Testes unitários para ambos (happy path + edge cases)
- README atualizado com documentação dos endpoints

Linguagem: Node.js/Express (TypeScript) | Testes: Jest

Apresente o plano de execução antes de começar. Aguarde minha aprovação.
O plano típico do Devin — o que revisar
Plano Devin → aguarda aprovação 
1. Ler estrutura do projeto
   (src/, package.json, tsconfig.json)

2. Criar src/routes/health.ts
   com implementação dos dois endpoints

3. Registrar rotas no app.ts principal

4. Criar __tests__/health.test.ts
   com testes Jest + supertest

⚠️ O que revisar antes de aprovar
  • Passo 1: Está lendo o tsconfig? TypeScript precisa de configuração correta para compilar.
  • Passo 2: O /health tem alguma dependência externa (banco, cache)? Se sim, remova — vai tornar o probe lento e instável.
  • Passos 4–5: Testes e docs estão no plano? Se não estiver aqui, não vai aparecer no output.
  • E3/E4: O plano menciona verificação de dados sensíveis no response? Se não, adicione como critério explícito no feedback ao plano.
O resultado (código gerado pelo Devin)
TypeScript src/routes/health.ts 
// GET /health — Kubernetes readiness/liveness probe
// Por quê: retorna apenas status e timestamp, sem dependências externas
// Qualquer adição de lógica complexa aqui aumenta o risco de falsa negativa
import { Router, Request, Response } from 'express';

const router = Router();
const startupTime = Date.now();

router.get('/health', (_req: Request, res: Response) => {
  res.status(200).json({
    status: 'ok',
    timestamp: new Date().toISOString()
  });
});

// GET /status — Informações operacionais para SRE
// Por quê: uptime calculado localmente, versão via ENV (nunca hardcoded)
// Sem dados de usuário, sem credenciais — compliance seguro
router.get('/status', (_req: Request, res: Response) => {
  const uptimeSeconds = Math.floor((Date.now() - startupTime) / 1000);
  res.status(200).json({
    service: 'auth-api',
    version: process.env.AUTH_API_VERSION || 'unknown',
    uptime_seconds: uptimeSeconds,
    timestamp: new Date().toISOString()
  });
});

export default router;
Exercício

Sua vez — endpoint /version

Cenário NTT: O time de SRE precisa rastrear qual versão de cada serviço está em produção para correlacionar com incidents.

Tarefa base (E1–E2–E3–E4)
Usar o Devin para implementar GET /version que retorna:
JSONResponse esperado
{
  "version": "1.2.3",       // de APP_VERSION
  "build_date": "2026-03-15T10:00:00Z",  // de BUILD_DATE
  "git_commit": "a1b2c3d"   // de GIT_COMMIT
}
Critérios de Conclusão
  • Endpoint /version responde com JSON válido contendo os três campos
  • Valores lidos de variáveis de ambiente (não hardcoded)
  • Dockerfile atualizado com as três ENV vars e valores de exemplo
  • Testes passando: happy path + caso de ENV var ausente (deve retornar "unknown")
Scaffold de Prompt (ponto de partida)
// Não é a solução — complete os campos em [colchetes] Contexto: API REST em [LINGUAGEM] para [TIPO_DE_SERVIÇO] no banco. Compliance: [LISTAR REQUISITOS]. Tarefa: Implementar GET /version que retorna... [VOCÊ COMPLETA DAQUI] Critérios de aceitação: [VOCÊ DEFINE COM BASE NOS CRITÉRIOS ACIMA]
Critérios de Conclusão — E2
  • Todos os critérios base (E1)
  • README atualizado com: descrição do endpoint, ENV vars necessárias, exemplo de curl
💡 No prompt, inclua: "Atualizar o README com uma seção de Configuração listando as ENV vars e um exemplo de request com curl."
⏱ Se ultrapassar 2h, identifique onde travou — isso é tão valioso quanto completar no tempo.
Dica para análise de plano
Para E2, o valor não é só completar — é analisar o plano do Devin antes de aprovar. Perguntas para fazer ao plano:

  • O Devin vai ler todos os arquivos relevantes?
  • Os testes cobrem o caso de ENV var ausente?
  • O README vai ser atualizado (está no plano)?
  • Há algum step que pode gerar dado sensível?
Critérios de Conclusão — E3
  • Todos os critérios base + E2
  • Nenhuma informação sensível pode aparecer no response ou nos logs
  • O prompt instrui o Devin a incluir comentário no código explicando por que cada campo é seguro para expor publicamente
🎯 Desafio adicional: Crie um template de prompt genérico para "adicionar endpoint de status operacional em qualquer microserviço NTT", reutilizável pelo time.
Para E3: trade-offs a avaliar
Auditabilidade: Código gerado por agente precisa ter o mesmo nível de comentários e rastreabilidade que código escrito manualmente?
Responsabilidade: Quem assina o PR gerado pelo Devin? O engenheiro que aprovou o plano tem responsabilidade total pelo código.
Compliance: Em ambientes com BACEN Resolução 4.658, código de sistemas críticos precisa de documentação de origem. Como documentar "gerado por Devin"?
Desafio E4 — Criar padrões para o time
Além de implementar o endpoint, produza os três artefatos que o time vai usar em todos os futuros labs:
1. Template de Prompt
Template com slots preenchíveis para qualquer serviço bancário. O time usa diretamente sem precisar reinventar a estrutura.
2. Checklist de Revisão
Checklist de code review para código gerado por agente em ambientes regulados (LGPD, BACEN, PCI-DSS).
3. Decisão Documentada
Quando usar Devin vs. desenvolver manualmente — critérios objetivos para o time tomar decisões consistentes.
Erros mais comuns — não caia nestas armadilhas
⚠️Prompt vago = output genérico: "Crie um endpoint de versão" sem contexto técnico vai gerar código que funciona mas não atende padrões do banco.
⚠️Editar código manualmente: Se o Devin gerar algo errado, não edite o arquivo — diga ao Devin o que está errado em linguagem natural.
⚠️Aprovar sem testar localmente: Sempre rodar npm test e testar o endpoint com curl antes de fazer merge.
⚠️Contexto bancário ausente: O Devin não assume LGPD, SLAs e compliance automaticamente. Sempre inclua explicitamente no prompt.
