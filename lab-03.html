LAB 03 · Fase Amplify

Automated Code Review

Configure o Design System como revisor permanente de PRs — detectando problemas de segurança, qualidade e compliance bancário antes que chegue à produção.

⏱ 4 horas 🔵 Design System E2–E3 Pré-req: LAB 02
Seção 01

Por que code review manual não escala em banco?

Em instituições financeiras, o custo de um PR mal revisado vai muito além de um bug técnico.

Em instituições financeiras, um PR mal revisado pode conter CPF exposto em log, API key hardcoded, cálculo financeiro incorreto ou ausência de tratamento de timeout — qualquer um desses em produção pode gerar notificação ao BACEN, recall de transações ou vazamento de dados pessoais sob LGPD.

O code review humano é lento, inconsistente e não escala com a velocidade de entregas que squads de alto desempenho precisam manter. A solução não é eliminar o review humano, mas amplificá-lo: deixar o agente cuidar do checklist mecânico enquanto o engenheiro foca em decisões de arquitetura.

R$ 2–8M
Custo estimado de um bug de segurança em produção bancária — entre multas BACEN, custo operacional de recall de transações e danos reputacionais mensuráveis.

Com o Claude Code configurado como revisor via AGENTS.md, cada PR recebe review automático, com regras customizadas para o contexto bancário, e feedback instantâneo antes do merge — sem depender da disponibilidade ou atenção de um colega.

  • Review automático em todo PR — sem gargalo humano para checklist mecânico
  • Regras customizadas: segurança, LGPD, BACEN 4.658, PCI-DSS
  • Feedback instantâneo no fluxo do desenvolvedor, antes do merge
  • Trilha de auditoria documentada para evidência em auditorias regulatórias
  • Consistência garantida: as mesmas regras aplicadas em todos os PRs de todos os times
Regulatório: O BACEN Resolução 4.658/2018 exige que instituições financeiras mantenham controles sobre o código que acessa dados de clientes. Review automatizado com regras documentadas é parte da evidência de controle exigida em auditorias.

Seção 03

O que você vai aprender

Três conceitos fundamentais que estruturam o automated code review em contexto bancário.

📋
AGENTS.md como Contrato de Review
O arquivo AGENTS.md é o "contrato" entre seu time e o agente revisor. Define o que o Claude Code deve verificar em cada PR: regras de segurança, padrões de código, checklist de compliance LGPD/BACEN. Uma vez configurado, o review é consistente em todos os PRs, sem depender da atenção humana.
🔍
Tipos de Problema Detectados
Segurança: PII em logs (CPF, conta, saldo), secrets hardcoded, SQL injection, headers inseguros.

Qualidade: Complexidade ciclomática alta, código duplicado, ausência de tratamento de erro.

Compliance: LGPD art.46 (medidas técnicas), BACEN 4.658 (controles de acesso), PCI-DSS (dados de cartão).
📊
Review por Diferencial de Nível
E2 configura o reviewer para um repositório.

E3 customiza regras por contexto bancário específico e cria templates reutilizáveis.

E4 define a estratégia de review para o time inteiro e mensura eficácia com métricas.

Exemplo de AGENTS.md

Este é o formato base que você vai criar no exercício. Adapte as regras ao contexto do seu projeto.

AGENTS.md # Code Review Rules — [Nome do Projeto] ## Segurança (CRÍTICO — bloqueia merge) - NUNCA logar dados pessoais: CPF, conta, saldo, nome completo, e-mail - NUNCA hardcodar: API keys, senhas, tokens, URLs de produção - SEMPRE validar input em endpoints públicos - SEMPRE usar HTTPS em chamadas externas ## LGPD / BACEN 4.658 - Dados pessoais devem ser mascarados em logs: "***" ou hash - Acesso a dados de cliente deve ter log de auditoria - Timeouts obrigatórios em chamadas a APIs externas (máx 10s para PIX) ## Qualidade - Funções com mais de 20 linhas precisam de comentário de propósito - Cobertura mínima de testes: 80% - Tratamento de erro obrigatório em toda chamada assíncrona ## O que NÃO revisar - Arquivos de configuração de ambiente (.env.example) - Documentação (*.md) - Gerado automaticamente (*.generated.*)
Seção 04

Cenário: PR com 3 problemas reais

Você vai revisar um PR de uma feature de consulta de saldo. O código tem 3 problemas intencionais que o reviewer deve detectar.

Este é o cenário do exercício. Um desenvolvedor abriu um PR adicionando o endpoint GET /saldo/:conta. O código parece funcional, mas contém 3 problemas críticos que seu reviewer configurado deve detectar antes do merge.

Problema 1 — CPF exposto em log

Dados pessoais logados em texto claro violam LGPD art. 46.

JavaScript // ❌ PROBLEMA: CPF exposto no log logger.info(`Consultando saldo para CPF: ${cliente.cpf}`); // ✅ CORRETO: Mascarar dado pessoal logger.info(`Consultando saldo para CPF: ***${cliente.cpf.slice(-3)}`);

Problema 2 — Timeout ausente

Chamada à API PIX sem timeout viola o SLA regulatório de 10 segundos.

JavaScript // ❌ PROBLEMA: Chamada sem timeout (viola SLA PIX de 10s) const saldo = await apiPix.consultarSaldo(conta); // ✅ CORRETO: Timeout explícito const saldo = await Promise.race([ apiPix.consultarSaldo(conta), new Promise((_, rej) => setTimeout(() => rej(new Error('timeout')), 9000) ) ]);

Problema 3 — Erro não tratado

Exceção não capturada pode expor stack trace ao cliente — risco de segurança e informação regulatória.

JavaScript // ❌ PROBLEMA: Erro da API não tratado — pode expor stack trace app.get('/saldo', async (req, res) => { const data = await buscarSaldo(req.params.conta); res.json(data); }); // ✅ CORRETO: Tratamento adequado app.get('/saldo', async (req, res) => { try { const data = await buscarSaldo(req.params.conta); res.json(data); } catch (err) { logger.error('Erro ao buscar saldo', { conta: req.params.conta, err: err.message }); res.status(500).json({ error: 'Serviço temporariamente indisponível' }); } });
Exercício: No exercício, você vai criar o AGENTS.md que detecta exatamente esses 3 padrões — e verificar que o reviewer os identifica corretamente antes de aprovar o PR.
Seção 05

Hora de praticar

Selecione seu nível para ver as instruções específicas de entrega.

E2 Configurar o reviewer básico ⏱ 2–3 horas

O objetivo do E2 é dominar a ferramenta: configurar o reviewer, usá-lo para detectar problemas reais e corrigir o código.

1
Fork do repositório de exercício
Faça fork do repositório: github.com/nttdata-forge/lab03-exercise. Clone localmente e abra no VS Code com o Claude Code ativado.
2
Criar o AGENTS.md
Crie o arquivo AGENTS.md na raiz do projeto com pelo menos 5 regras de segurança baseadas no exemplo da Seção 03.
3
Abrir o PR com o código problemático
Crie uma branch e abra um PR com o arquivo saldo-service.js que contém os 3 problemas mostrados na Demo.
4
Configurar o reviewer e executar
Configure o Claude Code para revisar o PR: claude review --pr [url]. Verifique que os 3 problemas são detectados.
5
Corrigir os 3 problemas
Aplique as correções mostradas na Demo: mascarar CPF no log, adicionar timeout na chamada PIX, e envolver o handler em try/catch com resposta controlada.
6
Documentar no PR
Adicione um comentário no PR documentando: quais problemas foram encontrados pelo reviewer, qual era o risco de cada um, e como foram corrigidos.
Critério de Aprovação E2

O reviewer detecta os 3 problemas (CPF em log, timeout ausente, erro não tratado) + PR aprovado após as correções + comentário de documentação presente.

E3 Review com compliance bancário ⏱ 3–4 horas

O E3 vai além da ferramenta: foco em compliance regulatório específico, decisões de arquitetura justificadas e criação de artefatos reutilizáveis para o time.

1
Complete o exercício E2
Todo o conteúdo do E2 é pré-requisito. O PR de saldo deve estar corrigido e aprovado antes de prosseguir para os passos E3.
2
Adicionar regras de compliance ao AGENTS.md
Expanda o AGENTS.md com seções específicas: LGPD art. 46 (medidas técnicas e administrativas de segurança), BACEN 4.658 (política de segurança cibernética e controles de acesso), PCI-DSS seção 6.3 (desenvolvimento seguro de aplicações de pagamento).
3
Criar PR com processamento de cartão
Crie um segundo PR com o código de processamento de cartão disponível no template do repositório. Este código contém problemas mais sutis do que o saldo-service.
4
Reviewer deve identificar 3 problemas de compliance
Configure o reviewer para identificar: dados de cartão sem tokenização (PCI-DSS), ausência de log de auditoria de acesso (BACEN 4.658), e endpoint sem autenticação expondo dados financeiros (LGPD).
5
Corrigir e documentar decisões arquiteturais
Corrija os problemas e, para cada decisão, documente: "Por que tokenizar aqui em vez de no serviço de pagamentos?", "Por que este formato de log de auditoria é suficiente para BACEN?", "Qual padrão de autenticação foi escolhido e por quê?"
6
Criar template reutilizável
Crie um arquivo AGENTS.md.template documentado e reutilizável para outros projetos do time, com comentários explicando quando ativar cada seção de regras.
Critério de Aprovação E3

AGENTS.md com seções de compliance LGPD/BACEN/PCI-DSS + template documentado e reutilizável + decisões arquiteturais justificadas em comentários no PR (mínimo 3 decisões com contexto regulatório).
