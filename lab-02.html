LAB 02 — API Orchestration with Kiro

No ecossistema bancário, uma única operação de negócio raramente é atendida por uma única API. Aprenda a orquestrar fluxos complexos de integração como código — com controle de estado, tratamento de erros, retries automáticos e SLAs do BACEN cumpridos sistematicamente.

⏱ 2h (E4) → 4h (E1) 🏷 E1–E4 🔀 Kiro 🏦 Contexto Bancário
Trilha Kiro
Contexto

Por que orquestração de APIs importa no banco

🏦
O problema: APIs em cadeia
Uma transferência PIX envolve validação de saldo, checagem de fraude, consulta ao BACEN, execução da transferência e disparo de notificações — em sequência, com dependências, com retry em falha, e com SLA de 10 segundos para o cliente. Fazer isso manualmente com chamadas HTTP em cadeia resulta em código frágil, difícil de manter e impossível de monitorar.
🎼
A solução: Kiro como maestro
O Kiro resolve esse problema: é uma ferramenta de orquestração de APIs e workflows que permite definir fluxos complexos de integração como código, com controle de estado, tratamento de erros, retries automáticos e logs estruturados. Para engenheiros NTT, dominar Kiro significa implementar integrações entre sistemas legados e APIs modernas com rastreabilidade completa e conformidade regulatória sistemática.

Conceitos Fundamentais

Vocabulário e arquitetura do Kiro

API Orchestration — conceitos centrais
Workflow
Definição declarativa de um fluxo de negócio. Composto por steps encadeados com entradas, saídas e condições de execução.
Step
Unidade atômica de execução dentro de um workflow. Pode chamar uma API HTTP, executar uma função, transformar dados ou chamar outro workflow.
Trigger
O que inicia o workflow — pode ser uma chamada HTTP, um evento em fila (Kafka, SQS), um agendamento (cron) ou outro workflow.
Context
Objeto compartilhado entre steps que carrega o estado da execução — inputs originais, outputs intermediários e metadados de rastreamento.
Error Handler
Lógica de recuperação por step ou por workflow — retry com backoff, fallback para valores default, ou compensação (rollback).
Integração com APIs bancárias brasileiras

Os bancos com os quais a NTT trabalha (Itaú, Nubank, Santander, Banco do Brasil, Bradesco) operam com os seguintes sistemas que o Kiro tipicamente orquestra:

PIX (BACEN SPI)
Sistema de Pagamentos Instantâneos — SLA de 10s para liquidação, disponível 24/7/365.
TED / DOC
Transferências entre bancos via STR (Sistema de Transferência de Reservas) — horários de janela operacional.
Open Finance
APIs padronizadas pelo BACEN para compartilhamento de dados — OAuth 2.0 obrigatório.
Core Banking
Sistemas internos de conta corrente, limites e saldo — latência variável, frequentemente legado.
Antifraude
Serviços internos ou terceirizados (ex: Konduto, ClearSale) — timeout crítico para UX.
BIAN Service Domains — mapeamento para orquestração

O BIAN (Banking Industry Architecture Network) define os domínios de serviço bancário de forma padronizada. Em workflows Kiro, cada BIAN Service Domain idealmente corresponde a um grupo lógico de steps, com separação clara de responsabilidade — facilitando manutenção, auditoria e reuso.

BIAN Service Domain O que representa Steps típicos no workflow
Customer Management Dados cadastrais e KYC do cliente Validar identidade, buscar perfil de risco
Payment Execution Service Execução de pagamentos (PIX, TED) Iniciar pagamento, confirmar liquidação
Account Management Saldo, limites e movimentação de conta Consultar saldo, reservar limite, debitar
Fraud Detection Análise de risco e antifraude Score de risco, bloqueio preventivo
Notification Management Comunicação ao cliente Push, SMS, e-mail pós-transação
Error handling e retry para SLAs bancários

O BACEN exige que transações PIX sejam liquidadas em até 10 segundos. Isso impõe regras específicas para retries:

Política de retry bancária padrão
- Timeout por step: 2s (APIs internas) / 5s (APIs externas)
- Max retries: 3 tentativas
- Backoff: exponencial (1s, 2s, 4s)
- Circuit breaker: após 5 falhas consecutivas, abrir por 30s
- Total máximo do workflow: 8s (margem de 2s para overhead de rede)
Retry sem estado
Repete toda a operação do zero. Adequado para operações idempotentes por natureza (consultas GET). Perigoso para operações de escrita financeira.
Retry com idempotência
Usa chave de idempotência para evitar duplicação de débito. Em contexto bancário, toda operação de escrita deve ser idempotente — obrigatório para chamadas ao SPI do BACEN.
Demonstração Prática

Workflow de análise de crédito

Cenário NTT
O banco precisa de um fluxo de análise de crédito para pré-aprovação de empréstimo pessoal. O fluxo consulta o saldo da conta, verifica o limite pré-aprovado e retorna uma decisão de crédito. Esse fluxo é chamado por 3 sistemas diferentes (app mobile, internet banking, gerente PJ) — por isso precisa ser um workflow Kiro centralizado, não lógica replicada em cada sistema.
YAML credit-assessment.workflow.yaml 
# workflows/credit-assessment.workflow.yaml
name: credit-assessment
version: "1.0"
description: "Avaliação de crédito - BIAN: Customer Management + Account Management"

trigger:
  type: http
  method: POST
  path: /workflows/credit-assessment
  auth: bearer

input:
  schema:
    customer_id:
      type: string
      required: true
    requested_amount:
      type: number
      required: true
      minimum: 100
      maximum: 50000
    product_type:
      type: string
      enum: [personal_loan, credit_card, overdraft]

steps:
  # BIAN: Customer Management — validar identidade e perfil
  - id: validate-customer
    name: "Validar cliente e status KYC"
    type: http
    config:
      url: "{{env.CORE_BANKING_URL}}/customers/{{input.customer_id}}"
      method: GET
      headers:
        Authorization: "Bearer {{env.CORE_BANKING_TOKEN}}"
        x-correlation-id: "{{workflow.execution_id}}"
      timeout: 2000
    retry:
      max_attempts: 3
      backoff: exponential
      initial_delay: 500
    on_error:
      action: fail
      message: "Cliente não encontrado ou KYC pendente"

  # BIAN: Account Management — consultar saldo
  - id: get-account-balance
    name: "Consultar saldo e limite disponível"
    type: http
    depends_on: [validate-customer]
    config:
      url: "{{env.CORE_BANKING_URL}}/accounts/{{steps.validate-customer.output.account_id}}/balance"
      method: GET
      headers:
        Authorization: "Bearer {{env.CORE_BANKING_TOKEN}}"
        x-correlation-id: "{{workflow.execution_id}}"
      timeout: 2000
    retry:
      max_attempts: 3
      backoff: exponential
      initial_delay: 500

  # BIAN: Customer Management — score de risco (serviço externo)
  - id: get-risk-score
    name: "Obter score de crédito"
    type: http
    depends_on: [validate-customer]
    config:
      url: "{{env.CREDIT_BUREAU_URL}}/score"
      method: POST
      headers:
        x-api-key: "{{env.CREDIT_BUREAU_KEY}}"
        x-correlation-id: "{{workflow.execution_id}}"
      body:
        # CPF mascarado no log — apenas os últimos 4 dígitos expostos para rastreamento
        document_hash: "{{steps.validate-customer.output.document_hash}}"
        product_type: "{{input.product_type}}"
      timeout: 3000
    retry:
      max_attempts: 2
      backoff: exponential
      initial_delay: 1000
    on_error:
      action: use_default
      default_output:
        score: 0
        recommendation: denied

  # BIAN: Payment Execution Service — decisão de crédito
  - id: credit-decision
    name: "Calcular decisão de crédito"
    type: function
    depends_on: [get-account-balance, get-risk-score]
    config:
      handler: "./handlers/credit-decision.handler"
      function: evaluate
      input:
        balance: "{{steps.get-account-balance.output.available_balance}}"
        score: "{{steps.get-risk-score.output.score}}"
        requested_amount: "{{input.requested_amount}}"
        product_type: "{{input.product_type}}"

output:
  decision: "{{steps.credit-decision.output.decision}}"
  approved_amount: "{{steps.credit-decision.output.approved_amount}}"
  interest_rate: "{{steps.credit-decision.output.interest_rate}}"
  valid_until: "{{steps.credit-decision.output.valid_until}}"
  execution_id: "{{workflow.execution_id}}"

logging:
  # LGPD: mascarar CPF e dados de conta em todos os logs
  mask_fields: [document, cpf, account_number, document_hash]
  level: info
  include_step_duration: true
TypeScript credit-decision.handler.ts 
// handlers/credit-decision.handler.ts

interface CreditDecisionInput {
  balance: number;
  score: number;
  requested_amount: number;
  product_type: 'personal_loan' | 'credit_card' | 'overdraft';
}

interface CreditDecisionOutput {
  decision: 'approved' | 'denied' | 'partial';
  approved_amount: number;
  interest_rate: number | null;
  valid_until: string | null;
  denial_reason?: string;
}

// Regras de negócio: baseadas nos parâmetros BACEN Resolução 4.966/2021
// Por quê: limites de exposição por produto são regulados — não é lógica livre
const SCORE_THRESHOLDS = {
  personal_loan: { minimum: 600, full_approval: 750 },
  credit_card:   { minimum: 500, full_approval: 700 },
  overdraft:     { minimum: 400, full_approval: 650 }
};

const RATE_TABLE: Record<string, Record<string, number>> = {
  personal_loan: { high: 0.0199, medium: 0.0289, low: 0.0399 },
  credit_card:   { high: 0.0799, medium: 0.0999, low: 0.1299 },
  overdraft:     { high: 0.0599, medium: 0.0799, low: 0.1099 }
};

export async function evaluate(input: CreditDecisionInput): Promise<CreditDecisionOutput> {
  const thresholds = SCORE_THRESHOLDS[input.product_type];
  const rates = RATE_TABLE[input.product_type];

  // Negar se score abaixo do mínimo
  if (input.score < thresholds.minimum) {
    return {
      decision: 'denied',
      approved_amount: 0,
      interest_rate: null,
      valid_until: null,
      denial_reason: 'score_below_minimum'
    };
  }

  // Negar se saldo insuficiente como garantia (regra interna do banco)
  if (input.balance < input.requested_amount * 0.1) {
    return {
      decision: 'denied',
      approved_amount: 0,
      interest_rate: null,
      valid_until: null,
      denial_reason: 'insufficient_balance_ratio'
    };
  }

  const scoreCategory = input.score >= thresholds.full_approval ? 'high'
    : input.score >= (thresholds.minimum + 100) ? 'medium'
    : 'low';

  const rate = rates[scoreCategory];

  // Aprovação parcial se score médio e valor alto
  const isPartial = scoreCategory === 'low' && input.requested_amount > 5000;
  const approved = isPartial
    ? Math.min(input.requested_amount * 0.5, 5000)
    : input.requested_amount;

  // Validade da oferta: 24h (padrão Open Finance)
  const validUntil = new Date(Date.now() + 24 * 60 * 60 * 1000).toISOString();

  return {
    decision: isPartial ? 'partial' : 'approved',
    approved_amount: approved,
    interest_rate: rate,
    valid_until: validUntil
  };
}

Exercício

Sua vez — Workflow de transferência PIX

Cenário NTT
O banco precisa de um workflow centralizado para transferências PIX que possa ser chamado por qualquer canal (app, internet banking, agência). O fluxo deve: validar saldo do remetente, checar regras de antifraude, executar a transferência via SPI (BACEN) e disparar notificações ao remetente e destinatário.
Implementar o workflow pix-transfer com 5 steps
1. validate-balance → Consultar saldo disponível (Account Management)
2. fraud-check → Score antifraude por transação (Fraud Detection)
3. execute-pix → Enviar para o SPI do BACEN (Payment Execution Service)
4. notify-sender → Notificar remetente (Notification Management)
5. notify-receiver → Notificar destinatário (Notification Management) [paralelo ao step 4]
Input esperado
{
  "sender_account_id": "acc_123",
  "receiver_pix_key": "destinatario@email.com",
  "amount": 250.00,
  "description": "Pagamento aluguel"
}
Critérios de Conclusão — Base (todos os níveis)
  • Workflow YAML com os 5 steps acima na ordem correta
  • Steps 4 e 5 executam em paralelo (sem depends_on linear entre eles)
  • Cada step com timeout adequado ao SLA PIX (total < 8s)
  • Output do workflow inclui transaction_id e status
Critérios extras — E2
  • Step validate-balance deve falhar o workflow com mensagem clara se saldo < amount
  • Step fraud-check deve ter fallback para score: 100 (conservador) se serviço indisponível
  • Step execute-pix deve ter política de retry com idempotência — incluir idempotency_key no header gerado a partir do execution_id
  • Step execute-pix não deve ter retry sem idempotência configurada (risco de débito duplo)
💡
Dica E2
A chave de idempotência deve ser derivada do workflow.execution_id, não gerada aleatoriamente a cada retry. Use {{workflow.execution_id}}-pix como valor do header x-idempotency-key.
Critérios extras — E3 (além de E2)
  • Todos os campos com CPF, chave PIX e número de conta mascarados no log (mask_fields no YAML)
  • Comentários no YAML mapeando cada step ao BIAN Service Domain correspondente
  • Handler TypeScript para fraud-check que loga o resultado sem expor dados do cliente
  • Incluir x-correlation-id gerado a partir do execution_id em todos os steps para rastreabilidade de ponta a ponta

Crie um template de workflow reutilizável para qualquer transferência bancária (PIX, TED, DOC) com slots configuráveis por tipo de operação. O template deve ter BIAN domain mapping embutido como comentários-padrão.

⚠️
Erro mais comum
Colocar os steps de notificação (4 e 5) em sequência quando eles poderiam rodar em paralelo. Um depends_on: [execute-pix] em ambos, sem dependência entre si, é suficiente para paralelismo. Economia real: se cada notificação leva 500ms, paralelo economiza 500ms no SLA total.
Pontos de Atenção
⚠️
Retry sem idempotência = risco de débito duplo
Em qualquer step que faz escrita financeira (débito, crédito, liquidação), retry sem chave de idempotência pode resultar em duplicação de operação. Toda chamada ao SPI do BACEN deve incluir x-idempotency-key persistente por execução, não gerado a cada tentativa.
⚠️
Timeout total ignora overhead de orquestração
O SLA PIX de 10s inclui o tempo do Kiro processando o workflow, não apenas o tempo das APIs externas. Configure os timeouts de cada step para que a soma mais o overhead de orquestração (~200ms por step) caiba no SLA total. Regra prática: deixe 20% do SLA como margem de orquestração.
⚠️
Dados sensíveis nos logs de erro
O campo mask_fields mascara dados em logs de sucesso, mas mensagens de erro geradas nos handlers podem expor CPF ou número de conta se não forem sanitizadas. Nunca inclua dados do cliente em error.message — use códigos de erro estruturados (ERR_BALANCE_INSUFFICIENT) e referencie apenas IDs internos nos logs.
⚠️
Paralelismo em steps com estado compartilhado
Steps que rodam em paralelo não devem escrever no mesmo recurso sem controle de concorrência. Notificações paralelas ao remetente e destinatário são seguras porque escrevem em filas distintas. Passos paralelos que atualizam o mesmo registro de conta precisam de lock explícito ou serialização.
